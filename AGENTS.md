# Repository Guidelines

## Project Overview

`resume-editor` is a browser-only, Chinese-language resume editor built as a Vite + React + TypeScript single-page app. Users manage multiple resumes, edit structured content, choose visual templates, tune layout, persist data locally, and export PDF or Word (`.docx`). There is no server, router, authentication, or remote data layer.

Treat local storage and generated files as the product boundary: changes must preserve existing resume data, keep export output usable, and work with both pointer/mouse and touch/keyboard input.

## Architecture & Data Flow

- `src/main.tsx` mounts `<App />` with React `StrictMode` and imports the global stylesheet.
- `src/App.tsx` is the application coordinator. It loads the store once, derives the selected resume, owns CRUD/save/export/error state, and passes callbacks into child components.
- The main UI flow is `App` → `ResumeManager` + `ResumeWorkspace`; `ResumeWorkspace` composes `TemplatePicker`, `ResumeEditor`, and interactive `ResumePreview`.
- Editor controls emit immutable `Resume` updates through `onChange`. `App` timestamps changed resumes, marks the store dirty, debounces local persistence by 300 ms, and flushes on `pagehide`.
- `src/store/resumeStore.ts` owns example/blank data, local-storage envelopes, validation, migration, normalization, generated IDs, and recovery backups. Storage keys are `resume-editor:v1` and `resume-editor:recovery`; the current envelope version is 2.
- `ResumePreview` derives display-safe content with `src/utils/resume.ts`, applies template/layout CSS variables, and renders `ResumeHeader` plus ordered/visible `ResumeSections`.
- Export uses a separate hidden, noninteractive preview. PDF export lazily loads `html2canvas` and `jspdf`, captures an A4-sized preview, and slices it into pages; DOCX export is generated by `src/utils/export.ts` with `docx`.
- `src/data/templates.ts` is the source of truth for the six template IDs: `classic`, `modern`, `minimal`, `editorial`, `executive`, and `compact`.

When modifying a data field or exported helper, trace every editor, preview, persistence, normalization, and export caller. Do not add a second state store or duplicate resume-shaping logic.

## Key Directories

- `src/components/`: feature UI and composition.
  - `editor/`: controlled section editors, repeatable item lists, bullets, and layout controls.
  - `preview/`: resume header, section rendering, and inline preview editing.
- `src/store/`: local-first store loading, migration, validation, and persistence.
- `src/types/`: shared `Resume`, `ResumeLayout`, item, and store contracts.
- `src/data/`: template metadata.
- `src/utils/`: content filtering/URL safety and PDF/DOCX export.
- `src/styles.css`: all application, template, responsive, print, motion, and accessibility-related styling.

## Development Commands

Install from the committed npm lockfile (the repository has no declared `packageManager` or engine version):

```bash
npm ci
npm run dev       # Start Vite development server
npm run build     # TypeScript project build, then Vite production build into dist/
npm run preview   # Serve the built dist/ output locally
```

`npm run build` is the only scripted type/production validation path. There are no repository scripts for linting, formatting, unit tests, coverage, or typecheck-only runs. Do not claim those checks were run unless a tool/config is added explicitly.

## Code Conventions & Common Patterns

- Use strict TypeScript as configured by `tsconfig.app.json`; avoid `any`, unused locals/parameters, and casing inconsistencies. Keep ESM imports and the existing semicolon-free, two-space TS/TSX style.
- Name React components and component files in PascalCase (`ResumePreview.tsx`); name functions, hooks, and local values in camelCase; use explicit union/type aliases for domain variants (`TemplateId`, `MobilePane`).
- Keep state ownership at the narrowest existing owner. `App` owns store/persistence/export state; feature components receive controlled values and callbacks rather than reaching into global mutable state.
- Update nested resume data immutably. Preserve item IDs when editing; create fresh IDs with `makeId()` for new or duplicated entities, and deep-copy arrays/objects when duplicating a resume.
- Keep persistence defensive: validate unknown local-storage data, normalize compatible shapes, preserve recovery behavior, and avoid assuming browser storage is always available.
- Keep browser-only APIs (`window`, `document`, `localStorage`, `crypto`, Blob URLs) behind the existing browser guards or browser execution paths. Export dependencies are intentionally lazy-loaded.
- Reuse `getResumeContent`, `toSafeExternalUrl`, `formatResumePeriod`, and template metadata instead of reimplementing filtering, URL handling, date display, or template decisions.
- Use semantic HTML, explicit labels, `aria-*` state, visible focus styles, keyboard Escape handling, focus restoration/trapping, and live status/alert roles when changing dialogs, drawers, menus, or tabs.
- CSS uses semantic kebab-case names with state modifiers such as `.resume-list-item.is-active`, and `:root` variables for shared colors/motion. Preserve the cascade: `src/styles.css` contains multiple later `@media (max-width: 768px)` blocks whose order intentionally overrides earlier mobile rules.
- Keep template-specific presentation in `.resume-<template>` selectors and layout state in the existing `resume-custom-order`, density, and alignment classes. Preserve `@media print` behavior and A4 dimensions when changing preview styles.
- For async work, follow the existing loading/error/focus pattern in `App` and `ExportMenu`; do not silently swallow export or save failures.

## Runtime/Tooling Preferences

- Use npm with `package-lock.json`; `npm ci` is the reproducible install choice. No Bun, pnpm, Yarn, Node version file, or package-manager field is configured.
- Use a browser-capable Node environment compatible with the locked Vite 6 toolchain (Vite's locked package declares Node 18+ compatibility). Exact project engine versions are not pinned.
- This is a client-rendered browser app, not an SSR application. PDF/DOCX export depends on browser layout, fonts, canvas, Blob downloads, and dynamic imports.
- Vite uses its defaults plus `@vitejs/plugin-react`; there are no configured aliases, environment variables, custom output paths, deployment files, or server APIs. Do not introduce environment-dependent behavior without documenting its source.

## Testing & QA

No automated test files, test runner, browser harness, CI workflow, lint configuration, formatter configuration, or coverage requirement exists in the repository. For every meaningful change:

1. Run `npm run build` to exercise strict TypeScript and the production bundle.
2. Run `npm run dev` and inspect the actual UI in a desktop viewport and a narrow mobile viewport.
3. For UI changes, verify keyboard focus/activation and touch/pointer interactions, not only visual appearance.
4. For resume model changes, edit, duplicate, rename, delete, reload, and confirm local data remains valid; check malformed-data recovery if storage logic changed.
5. For export changes, generate both PDF and DOCX, verify non-empty output, filename sanitization, links, typography, and A4/page-break layout.

Responsive acceptance is part of QA. Check desktop multi-column layout, tablet pane behavior around the existing `1100px`/`768px` boundaries, and small screens around `480px`/`380px`. Confirm the mobile editor/preview switcher, resume-manager drawer, export modal, collapsed template/layout controls, safe-area spacing, minimum touch targets, and `prefers-reduced-motion`. Preserve print output while making responsive changes.
